# Работа над Qmanga

## Контекст и задачи

- Выполняй текущий запрос владельца. Наличие пункта в плане само по себе не поручает его реализацию.
- Для продуктовых изменений выполняй `bun run backlog instructions overview` и читай целевую карточку через `bun run backlog task view TASK-ID --plain`. Единственная очередь — `backlog/tasks/`; [UPDATE.md](UPDATE.md) хранит общие требования и порядок этапов. Обновляй карточки через CLI, не редактируй их Markdown вручную. [План развития](docs/DEVELOPMENT-PLAN-2026-10-18.md) — исходный технический backlog T01–T35, а не список гарантированно незавершённых задач.
- [Контрольная точка](docs/CURRENT-STATE-2026-10-18.md) и отчёты содержат результаты на указанные даты. Перед работой сверь выбранную задачу с актуальным кодом, Git и доступными проверками; не повторяй уже выполненное и не считай старый успешный прогон проверкой текущего состояния.
- Читай только относящиеся к задаче документы. Для кода соблюдай [архитектуру](docs/ARCHITECTURE.md); для интерфейса также `apps/web/AGENTS.md` и [актуальные решения по дизайну](docs/ui/DESIGN-REVIEW.md).

## Порядок работы

- Делай коммиты часто и самостоятельно: после каждого небольшого логически завершённого и проверенного изменения, не накапливая всю сессию в одном коммите. Перед коммитом проверь diff и выполни подходящие проверки; включай только относящиеся к изменению файлы. Пиши понятное сообщение о результате. Push выполняй по запросу владельца.
- Для нетривиальной задачи коротко обозначь цель, критерии готовности и границы. Если реализация продолжается между сессиями, сохрани несколько шагов рядом с существующим пунктом задачи.
- Рутинные действия в согласованных границах выполняй самостоятельно. Новые соседние функции не добавляй без запроса. При расхождении плана с кодом исправь описание выбранного пункта, сохранив невыполненные критерии.
- Если несколько исполнителей уже участвуют в работе, у задачи должен быть один ответственный; согласуй пересекающиеся файлы. Это правило не требует запускать дополнительных агентов.
- Завершая работу, укажи в том же пункте: что изменено, какие проверки выполнены и их результат, что осталось. Для маленькой правки документации достаточно итогового ответа и проверки ссылок/разницы.
- Различай «реализовано», «проверено локально» и «выпущено». В Backlog.md статус Done означает подтверждённые критерии и завершённую приёмку; для продуктовой задачи с требованием выпуска до выпуска оставляй Review. Перенесённые Done имеют историческое подтверждение из исходного UPDATE.md, а не новый прогон. Локальная проверка не подтверждает выпуск. Невыполненные проверки и внешние ограничения указывай явно.
- Если работа не закончена, оставь конкретный следующий шаг и блокирующее условие, если оно есть. Не сохраняй временные токены, пароли или личные данные в заметках.

## Документация без разрастания

- Обновляй существующий пункт задачи и профильную инструкцию вместо нового плана, аудита или отчёта на каждую сессию. Не дублируй очередь в нескольких местах.
- Новый документ нужен только для самостоятельной темы, которую нельзя понятно разместить в существующем. Длинные логи, скриншоты и временные данные держи в игнорируемой папке `tmp/`.
- Перед созданием карточки ищи существующую, чтобы не дублировать задачу. Для начатой работы указывай ответственного, статус In Progress и короткий план; затем результаты проверок и следующий шаг. Не переноси другие исторические планы в карточки без запроса. Доска, CLI или MCP нужны только при реальной необходимости; установка инструментов не является условием работы над проектом.
