# Qmanga: план развития после аудита

Дата: 18 октября 2026 года. Основание: [аудит с доказательствами и ограничениями](AUDIT-2026-10-18.md), срез `46737a0`.

## Цель и порядок работы

Следующий результат — закрытая бета, в которой читатель, команда перевода и сотрудник проходят основные задачи без ручной помощи разработчика. Затем — доказанная готовность к публичному запуску. Существующий стек, модульный монолит, зелёная палитра, две темы и направление компактного каталога сохраняются.

Идентификаторы A01–A20 ссылаются на аудит. Оценка трудоёмкости относительная: S — локальное изменение, M — несколько слоёв и сценариев, L — отдельная подсистема или значительное согласование данных. Это не обещание календарных сроков. Реальный план итерации составляется после уточнения исполнителей; одновременно достаточно 2–3 задач.

Не начинать весь backlog сразу. Каждый блок закрывается проверяемым пользовательским результатом. Исправления сопровождать регрессионными тестами по поведению; изменения текста/отступов не требуют искусственных тестов, повторяющих реализацию.

## Этап 1. Воспроизводимый запуск и доверие к основным действиям

**Результат:** новый разработчик поднимает проект по инструкции, а главные переходы и состояния не вводят пользователя в заблуждение.

| Задача | Основание | Размер / ответственный | Критерий завершения |
| --- | --- | --- | --- |
| T01. Исправить общий API/worker image и холодный старт | A01 | S–M, backend/infra | На чистом image cache одна документированная команда собирает и запускает все основные сервисы; работает другое имя Compose-проекта |
| T02. Привести publishing smoke к текущему attribution-контракту | A02 | S, backend | Штатный сценарий проходит без временных правок; отсутствие подтверждения прав остаётся отрицательной проверкой |
| T03. Определить staff просмотр проекта и исправить ссылку | A03 | M, backend + frontend | Admin вне команды получает разрешённый рабочий экран; member не приобретает права editor; moderator видит только предусмотренные действия |
| T04. Убрать ложное «Сохранено» и разделить состояния формы | A04 | S, frontend | Первичное открытие/выбор не дают success; success появляется после подтверждённой записи; отказ сохраняет ввод |
| T05. Ввести минимальный браузерный регрессионный набор и CI | A19 | M, full stack | PR проверяет сборку, unit/integration и staff navigation; release-проверка включает auth/publish/read и не скрывает skips |
| T06. Обновить стартовую документацию и recovery локальной среды | A01, раздел DX | S, maintainer | Один актуальный маршрут установки; отдельно описан случай старых volumes и отсутствующего env; нет предложения удалить данные ради запуска |

**Первый пакет работы:** T01 → T02 → T03 → T04; тесты из T05 добавляются вместе с исправлениями, T06 завершается на фактически проверенном пути. Это компактный законченный результат, а не начало нового редизайна.

Приёмка этапа: новый checkout/чистая тестовая среда → setup → запуск → синтетическая глава → публикация → чтение. Прогон должен быть выполним вторым человеком без устных пояснений автора.

## Этап 2. Целостный путь читателя

**Результат:** библиотека и продолжение достоверны, длинная серия находится полностью, скачанный контент доступен с автономного стартового экрана.

| Задача | Основание | Размер | Критерий завершения |
| --- | --- | --- | --- |
| T07. Серверные фильтры библиотеки/проектов и честные counts | A06 | M | При >100 записях совпадение на дальнейшей странице находится без ручной загрузки всех предыдущих; фильтр сбрасывает cursor; пустое состояние действительно пустое |
| T08. Подключить серверный поиск/сортировку глав в reader | A07 | M | В серии с 300+ главами поиск далёкого номера/имени находит результат сразу; переключение сортировки не теряет/дублирует главы |
| T09. Создать read model недавнего чтения | A08, A10 | M | Последний прочитанный тайтл первым для аккаунта и гостя; есть собственная обложка, позиция и доступность; список не сканирует всю библиотеку |
| T10. Устранить N+1 библиотеки | A10 | S–M | Число запросов не растёт линейно с числом элементов; integration проверяет тот же прогресс и unseen; есть замер до/после |
| T11. Сделать автономный список скачанного | A09 | M–L | После перезапуска браузера без сети можно открыть список, выбрать любую из двух полностью скачанных глав, читать и вернуться в список |
| T12. Завершить состояния offline/update | A09, риск обновления SW | M | Неполная/вытесненная копия объяснена; есть восстановление после сети; обновление приложения не ломает уже открытый reader и не удаляет выбранные скачивания |
| T13. Независимая обложка тайтла | A05 | M–L | Обложка добавляется до первой главы, безопасно обрабатывается, сохраняется при публикации/исправлении следующей главы; отзыв имеет явную политику |

Зависимости: T09 проектируется вместе с T10 и контрактом cover T13. T11/T12 проверяются вместе, потому что отдельная закэшированная страница ещё не означает законченный offline journey. T07 для рабочих проектов может идти параллельно читательской части.

Проверки reader: обычное/обратное управление, полосовой режим, смена качества, возврат после reload, guest → account, два аккаунта на устройстве, конфликт двух вкладок, отозванная публикация и недоступная сеть. Использовать малую быструю fixture для CI и отдельную длинную для устройств.

Приёмка этапа: новый читатель без пояснений находит произведение, читает, возвращается к последнему месту; затем повторяет путь через скачанный список без сети. Нельзя закрывать этап только API-тестами.

## Этап 3. Работа переводчиков, модерации и поддержки

**Результат:** команда готовит и исправляет контент без лишней повторной работы, сотрудник принимает решение по контексту и видит его историю.

| Задача | Основание | Размер | Критерий завершения |
| --- | --- | --- | --- |
| T14. Визуальная проверка страниц | A11 | M | Миниатюры, увеличение, действительный staged-порядок, ошибки на конкретных страницах; reorder доступен без мыши; исходники остаются приватными |
| T15. Защита несохранённых правок | A12 | M | Порядок/attribution не теряются молча при уходе; save/conflict/retry понятны; после отказа введённое сохраняется |
| T16. Исправление через новую ревизию с reuse assets | A12 | L | Для замены одной страницы не требуется повторно загрузить всю главу; старая опубликованная версия неизменна; новая проходит проверку |
| T17. Управление приглашениями и составом | A13 | M–L | Владелец видит pending/expired, отзывает и повторяет приглашение, изменяет разрешённые роли; продумана передача владения и защита последнего owner |
| T18. Контекстная карточка обращения | A14 | M | Видны тайтл/глава/страница или комментарий с необходимым окружением, причина, история и результат; обычная жалоба решается без поиска UUID вне UI |
| T19. Рабочая очередь и читаемый audit log | A15 | M | Сортировка по времени/приоритету, фильтры, ссылки и old/new для значимых изменений; конкурентное решение не затирает чужую работу |
| T20. Разделить рабочий список и редактирование каталога | UI/admin | M | Есть поиск выбора тайтла; отдельная карточка сохраняет контекст; вторичные операции не раздувают основную форму; ошибки и успех точны |

До реализации T17 владельцу продукта нужно выбрать простую модель передачи команды и полномочий. Это продуктовый выбор, а не причина останавливать T14/T15/T18. Для T19 назначение конкретного модератора добавлять только при реальной совместной работе нескольких сотрудников.

Приёмка этапа: представитель команды подготавливает главу из 50+ страниц, находит неверный порядок, получает отказ, исправляет и повторно отправляет. Другой человек проводит модерацию и объясняет результат по интерфейсу, не открывая БД. Тестовый отказ не должен уничтожать работу команды.

## Этап 4. Проверка UX, языка и доступности на реальных задачах

Этот этап идёт небольшими порциями вместе с этапами 2–3. Финальная проверка выполняется на стабилизированных сценариях, а не на пустой галерее компонентов.

| Задача | Размер | Критерий завершения |
| --- | --- | --- |
| T21. Уплотнить карточку тайтла и библиотеку вокруг чтения | M | Читать/продолжить заметнее вторичных настроек; предпочтения раскрываются по запросу; главы доступны без длинного прохода через формы |
| T22. Довести kk/ru системные сообщения и терминологию | M | Письмо и уведомление соответствуют выбранной локали; ошибки, даты, plural forms и accessibility labels покрыты; пользовательский контент не переводится |
| T23. Матрица состояний UI | M | 320/360/1280 px, обе темы/локали, длинный текст, empty/loading/error/forbidden/conflict имеют проверенные варианты |
| T24. Клавиатура и средства доступности | M | Порядок фокуса, модальные панели/возврат фокуса, увеличение текста, reduced motion; основные задачи проходят с клавиатурой и выбранным screen reader |
| T25. Физические устройства | M, зависит от доступа к устройствам | На выбранном слабом Android: длинная глава, длительное чтение, потеря сети, фон/возврат, смена качества; отдельно проверен поддерживаемый iOS/Safari |
| T26. Короткие исследования с читателями и командой | M | Зафиксированы завершение задачи без помощи, ошибки, время/затруднения и конкретные изменения; предпочтение цвета не заменяет результат задачи |

Практичный первый раунд: несколько казахоязычных и русскоязычных читателей, минимум один человек, регулярно готовящий главы, и человек, который будет модерировать. Такая выборка выявляет проблемы, но не является статистическим доказательством удобства для всей аудитории.

Для каждой сессии заранее задать задачи: найти нужный перевод; продолжить вчерашнее; скачать и открыть без сети; исправить неверную страницу; разобраться в жалобе. Наблюдать без подсказок, фиксировать реальный тупик, затем перепроверять исправленный сценарий.

## Этап 5. Эксплуатация и условия публичного запуска

**Результат:** систему можно наблюдать, безопасно развёртывать, восстанавливать и обслуживать. Эти задачи можно начинать раньше, но нельзя считать закрытыми по наличию конфигурационного файла.

| Задача | Основание / размер | Критерий завершения |
| --- | --- | --- |
| T27. Доверенные прокси и rate limiting | A17 / M | Разные реальные клиенты не делят случайный общий лимит; поддельный forwarding header не обходит ограничение; API не открыт в обход gateway |
| T28. Production-конфигурация и секреты | A18 / M | TLS, origin/cookie/CSRF, внешняя SMTP-доставка, ограниченные MinIO credentials, веб-заголовки и изоляция сервисов проверены на staging |
| T29. Backup и практическое восстановление | A18 / L | На чистой среде восстановлены БД и оба bucket; читаются главы, права и приватность сохранены; замерены время восстановления и потеря данных |
| T30. Наблюдаемость и runbooks | A18 / M–L | Оповещение при остановке полезной работы worker, росте очереди, ошибках выдачи/почты и диске; по request/job ID можно найти причину; описаны действия дежурного |
| T31. Миграции, релиз и rollback | A18 / M | Проверен upgrade с предыдущей версии, совместимость открытых клиентов, откат приложения с учётом схемы; утверждён порядок действий при неоткатываемой миграции |
| T32. Политика хранения и очистка | A18 / M–L | Определены сроки source/orphan/token/session/log; пробный режим очистки и защита используемых объектов; удаление не ломает published/offline manifests |
| T33. Нагрузка и стоимость | A10/A18 / M | Репрезентативные объёмы каталога/глав/аккаунтов, планы SQL, число запросов, p95 и память на выбранном устройстве; понятны storage/egress/processing costs |
| T34. Работа с контентом и обращениями | Раздел эксплуатации / M, продукт + операторы | Есть ответственные, правила публикации и обработки жалоб, контакт, согласованная политика данных и порядок пересмотра решений |
| T35. Защита staff и аудит зависимостей | Security / M | Выбран способ усиленной защиты staff, управление сессиями; scanner входит в регулярную проверку; риски разобраны, а не только сформирован отчёт |

Для T29 владелец задаёт допустимую потерю данных и время восстановления. Для T33 сначала определить целевой объём и устройство, затем измерять. Не заявлять «поддерживаем N пользователей» по одному локальному запуску.

## Этап 6. Развитие по данным после стабилизации

1. Ввести минимальную воронку чтения и показатели качества: успешная первая страница, восстановление позиции, скачивание, возврат, публикация и обработка жалобы.
2. Уточнить полки главной: что значит «популярное», за какой период, как учитывать малое число оценок и не путать аккаунтный прогресс со всеми читателями.
3. Довести SEO публичных страниц: canonical, метаданные шаринга, sitemap, правила индексации, отсутствие дублирования description. Закрытые разделы не индексировать.
4. Измерить, что действительно мешает читателям и командам. Убирать лишние действия прежде, чем добавлять новые разделы.
5. Расширять функции только при подтверждённой задаче и понятной операционной стоимости. Отдельно оценивать полезность подборок, персональных рекомендаций, расширенных командных инструментов и установочного PWA-пути.

Платежи, личные сообщения, социальная лента, нативные приложения и микросервисы не входят в ближайшие этапы. Для них пока не доказана более высокая ценность, чем у исправления существующего пути чтения и публикации.

## Условия перехода между состояниями продукта

### Можно расширять закрытую бету

- T01–T13 закрыты или оставшиеся ограничения явно приняты владельцем для ограниченной аудитории; основные дефекты не маскируются формулировкой «MVP».
- Есть автоматические проверки публикации, продолжения, staff navigation и автономного входа.
- Команда и модератор могут работать с тестовым контентом без прямого редактирования БД.
- На выбранных устройствах проверен реальный путь чтения; найденные блокирующие проблемы устранены.
- Существует способ восстановить тестовые/бетаданные и получить сведения о сбое.

### Можно рассматривать публичный запуск

- Завершены обязательные эксплуатационные T27–T35 в согласованном объёме, а не только записаны в backlog.
- Восстановление из backup и релиз/rollback выполнены практически.
- Нет открытых P1, ломающих чтение, публикацию, права или работу модерации.
- Есть разрешённый контент, ответственные за публикацию и жалобы, понятные пользовательские правила.
- Измерена базовая производительность и определены допустимые ограничения.
- Проведены пользовательские и языковые проверки, остающиеся ограничения сообщаются честно.

## Метрики плана

| Что хотим улучшить | Как проверять |
| --- | --- |
| Воспроизводимость | Доля успешных чистых запусков/приёмок; ручные шаги и время нового разработчика |
| Начало чтения | Успешный показ первой страницы после выбора тайтла; время и ошибки |
| Возвращение | Доля корректных продолжений последнего чтения; жалобы на потерю/перезапись позиции |
| Офлайн | Доля полных скачиваний и успешных стартов без сети; случаи вытеснения/повреждения |
| Работа команды | Время от загрузки до отправки; повторные загрузки; ошибки порядка и возвраты |
| Модерация | Возраст ожидающей очереди, время решения, доля повторных обращений и пересмотров |
| Эксплуатация | Ошибки выдачи, возраст jobs, время обработки, свободное место, результаты backup restore |
| Реальная ценность | Возврат пользователей по когортам, повторное чтение и обратная связь по задачам |

Численные цели задавать после исходного замера. Не превращать количество коммитов, компонентов или зелёных assertions в показатель качества пользовательского опыта.

## Правило завершения задачи

Задача считается завершённой, когда описанный сценарий работает на нужных ролях и данных, ошибки объясняются, существенная регрессия защищена проверкой, а актуальная инструкция соответствует результату. Для визуальной задачи нужны просмотр реального экрана и состояния; для эксплуатационной — исполненная процедура; для продуктовой гипотезы — наблюдение пользователей или измерение, а не мнение разработчика.
