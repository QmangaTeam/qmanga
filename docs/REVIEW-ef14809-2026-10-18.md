## R01 — ошибка поиска превращается в пустую библиотеку, P2

**Воспроизведено в браузере.** На авторизованном экране библиотеки временно подставлен HTTP 500 только для одного запроса поиска через средства разработчика. После завершения запроса пользователь увидел сообщение об отсутствии тайтлов, без объяснения сбоя и повтора. В журнале браузера остался необработанный `ApiFailure`. Серверные данные и сам сервер при этом не изменялись; перехват снят сразу после проверки.

Причина: [Library.svelte:47](../apps/web/src/lib/features/reading/presentation/Library.svelte#L47) и обработчик фильтра вызывают `directory.search()` без обработки rejection. Directory перед запросом очищает список и total, а в finally снимает busy. Отдельного состояния ошибки нет, поэтому UI принимает отказ за пустой результат. Прежний компонент ловил такую ошибку в общем load.

По коду тот же пробел есть у прямых вызовов `directory.more()` в библиотеке и [Projects.svelte:54](../apps/web/src/lib/features/publishing/presentation/Projects.svelte#L54), а также у callback refresh после синхронизации. Ошибка «Ещё проекты» вручную не моделировалась; это дополнительная область проверки того же контракта.

**Что исправить:** явное состояние ошибки/повтора для search, filter, more и refresh; при добавочной загрузке сохранять уже показанные строки. Ошибки устаревших запросов не должны перекрывать успешный актуальный запрос.

**Приёмка:** подставить 500 и истёкшую сессию для каждой операции; пользователь видит причину и следующий шаг, а не ложное пустое состояние. После восстановления запрос успешно повторяется с применёнными criteria.

## R02 — два изменения из одной вкладки создают конфликт версий, P2

**Воспроизведено с настоящим API и временной задержкой запроса.** В синтетическую библиотеку добавлен один тестовый тайтл. Статус изменён `reading → planned`; первый PUT временно задержан. Поле оставалось доступно, поэтому сразу задан `completed`. После продолжения первого запроса возникло сообщение о конфликте с другим устройством, хотя оба изменения сделаны из одной вкладки. Одновременно был виден success «Сақталды» («Сохранено»).

Причина: [Library.svelte:59](../apps/web/src/lib/features/reading/presentation/Library.svelte#L59) проверяет `directory.busy`, но не устанавливает состояние записи на время `save`. Busy directory относится к получению списка. Второй выбор получает ту же версию записи, что первый. LibrarySync последовательно отправляет операции, но снимок второй операции уже содержит старую версию; сервер корректно отвечает конфликтом. Это ложный для пользователя межустройственный конфликт, а не ошибка серверной защиты версий.

**Что исправить:** отдельное состояние изменения записи и управляемая сериализация/объединение выбора. Можно блокировать управление строкой до результата или поддержать последнее намерение с актуальной версией. Нельзя убирать проверку версий на сервере. Success должен относиться к завершённому актуальному действию и не противоречить pending/conflict.

**Приёмка:** при задержанном PUT выполнить два изменения статуса и статус + favorite. Последний принятый выбор сохраняется без искусственного конфликта; интерфейс объясняет ожидание и не сообщает об успехе незавершённого действия. Настоящий конфликт с другой вкладкой остаётся управляемым.

После проверки конфликт разрешён, добавленная тестовая запись убрана обычным действием продукта, библиотека снова показывает total=0. Тестовая учётная запись закрыта выходом.

## R03 — локальная проверка поиска расходится с серверной, P2

**Подтверждено кодом и отдельной исполняемой проверкой application-класса; не воспроизводилось браузером на реальном alias.** Серверный [поиск библиотеки](../backend/internal/reading/adapters/postgres/library.go#L17) учитывает `name_kk`, `name_original` и `aliases`. Новый [LibraryDirectory.matches](../apps/web/src/lib/features/reading/application/library-directory.ts#L21) проверяет только `item.name`.

Сценарий: сервер нашёл тайтл по оригинальному/альтернативному названию, которого нет в отображаемом казахском имени. Пользователь меняет только favorite, изменение остаётся pending. `applyPendingUpdate` заново проверяет строку по одному имени и удаляет её из выдачи, хотя поиск и статус не менялись.

Изолированная проверка на текущем коде: до pending update — 1 строка, ожидается 1 после изменения favorite, фактически — 0. При этом partial корректно становится true, но само исчезновение неверно.

**Что исправить:** согласовать локальную проверку с серверным контрактом. Для уже подтверждённого сервером совпадения при изменении статуса/favorite не требуется заново опровергать совпадение по неполному набору текстовых полей. Для автономного поиска отдельно определить доступные метаданные и честные ограничения.

**Приёмка:** тайтлы, найденные по казахскому имени, оригинальному имени и alias; затем pending-изменение favorite и переход в/из выбранного статуса. Строки исчезают только при реальном выходе из применённого фильтра.
