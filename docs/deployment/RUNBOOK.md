# Qmanga deployment runbook

The public names are `qmanga-dev.maqsatto.dev` (staging) and `qmanga.maqsatto.dev` (production). Both may share one Oracle Ampere A1 host, but use separate Compose projects, PostgreSQL databases, MinIO volumes and credentials. This is **one-host fault tolerance during application updates**, not high availability if Oracle, the VM, its disk or the network fails.

## Development, integration and acceptance contract

This section is the working contract for Backlog tasks, not evidence that a particular release passed. Use the existing [architecture boundaries](../ARCHITECTURE.md) and [local test environment](../LOCAL-DEVELOPMENT.md).

1. Read the selected Backlog task, dependencies and acceptance criteria; compare them with current code. Assign one owner, set `In Progress`, and record the current plan in that card. Keep each change independently reviewable and commit after appropriate checks. A task on the board is not authorization to expand the current request.
2. Choose checks at the boundary that can fail. For a bug, reproduce it with a failing regression before the fix. Add browser regressions to `apps/web/tests/browser/*.test.mjs`; the existing CI glob includes new files automatically. A static/SSR check does not replace interaction or real persistence checks.

| Change boundary | Contract to preserve | Required evidence for that change |
| --- | --- | --- |
| Presentation → application | Existing ports, truthful loading/error/success state, retained input on errors, kk/ru, both themes, keyboard and reduced motion | Frontend application and SSR tests, app/preview diagnostics, architecture/contrast, production build; browser regression at 320/360/desktop for changed interactions |
| HTTP → use case → PostgreSQL | Auth/role enforcement, validated DTOs, explicit conflict/version semantics, correct transaction boundaries, persisted results | Relevant Go unit/adapter/HTTP tests and real PostgreSQL integration; browser/API acceptance for the affected user journey |
| Publishing → worker → media gateway | Private originals, immutable public revisions, safe codecs, retry behavior and authorized derivative delivery | Real PostgreSQL/codec suite plus synthetic publish/read smoke; test replacements against the existing published revision |
| Browser → offline storage | Account isolation, saved-byte completeness, no false success or position loss, safe cache/schema updates | Browser offline/eviction/retry regression with an isolated context; no production fixtures |
| Schema / HTTP shape / cache format | Previous deployed app keeps working during the rollback window; old clients/data remain readable or have an explicit transition | Backward-compatible migration/adapter tests; document the rollout sequence in the card before changing the contract |
| CI / Backlog / deployment | Locked dependencies, acyclic task identities/dependencies, complete test results, tested SHA only | Locked install and `backlog doctor`, config/shell checks and affected release/backup tests; observed Actions result before claiming remote CI success |

3. Run local checks in a disposable environment where data fixtures are needed. Never point seeding or cleanup at production, or reuse the owner's real data as a fixture. Keep credentials in ignored env/fixture files. Use serial full builds to avoid memory pressure. For UI changes rebuild and inspect the integrated Docker web service, not just a preview.
4. Record the code commit SHA, commands/results, failed or unperformed checks, and the concrete next step in the same card. Keep screenshots/logs under ignored `tmp/`; don't create a new report per session. Set `Review` after implementation when remote CI, user acceptance or release gates remain. Docs/tooling tasks may be `Done` after their own verified criteria; product tasks requiring release remain `Review` until that release is observed.
5. On an authorized push/PR, `Verify Qmanga` checks locked Backlog data, setup/deployment definitions, cold Docker start, full Go/PostgreSQL/codec tests without actual skips, auth/publishing/reading smoke, and all browser regressions. Images publish only after successful acceptance on `main`. Inspect the run for the **same SHA**; workflow configuration or a local green build is not a remote result. Push remains subject to the owner's working instructions.
6. On staging, verify that exact SHA, readiness and the changed user journey, including failure/role cases. The host poller and optional GitHub staging job are described below; don't enable a second deployment path or change host access as part of a product task. Record the observed environment/SHA/checks in the card.
7. Promote the same staging images through the existing production gates: verified off-host backup, restore drill, SMTP and health checks. Observe the public changed journey, then mark the product task `Done`. If the candidate fails, use the existing application rollback; database writes and migrations are not reverted. A destructive restore needs its own maintenance decision. No automatic force-push, schema rollback or volume deletion is part of ordinary development.

## Before the first release

1. In the Oracle home region, check actual Always Free capacity and create an **ARM64** Ubuntu VM with at least 2 OCPU, 12 GB RAM and enough persistent disk for two sites, two warm application versions and two backups. Reserve a stable public IP if available. Keep a separate off-host backup destination; a second folder on this VM is insufficient.
2. Set OCI network rules and the Ubuntu host firewall for inbound TCP 80/443 from the internet and TCP 22 only from the operator's allowed source. Oracle's Ubuntu image has a separate iptables `INPUT` rejection rule; add 80/443 before that rule and persist the change in `/etc/iptables/rules.v4`. Do not expose PostgreSQL, MinIO, API or gateway ports. Install Docker Engine with Compose v2, Git, curl, sha256sum and `flock`. Create a dedicated deploy account and install its **public** SSH key. Docker group access effectively grants root-equivalent host control; restrict this account and key.
3. Create DNS A records for both names pointing to the VM public IP. Do not add AAAA records unless IPv6 is configured and reachable. Confirm both names resolve before expecting TLS issuance.
4. Under `/opt/qmanga`, create `repo`, `config`, `state/sites`, `backups`, `bin` and `hooks`. Clone the public repository into `repo`, owned by the deploy account. Copy `deploy/host.env.example` to `config/staging.env` and `config/production.env`, adjusting target and origin. Generate distinct high-entropy alphanumeric secrets for each environment. Set owner-only permissions (`chmod 600`) on both files. Configure real STARTTLS SMTP and a working sender address. Keep all secrets outside Git and GitHub logs.
5. The published GHCR images are public, so the deploy account can pull them without a registry token. If package visibility changes, configure a read-only `read:packages` token in the account's protected home.
6. The VM uses an outbound-only systemd poller for staging. Install `jq`, copy `deploy/qmanga-staging-poll.{service,timer}` to `/etc/systemd/system/`, run `systemctl daemon-reload`, then `systemctl enable --now qmanga-staging-poll.timer`. Keep `QMANGA_STAGING_ENABLED` unset: the alternate GitHub-hosted SSH deployment path is intentionally disabled, since TCP 22 is restricted to the operator IP. A successful push or manual `Verify Qmanga` run publishes all three ARM64 images; the poller checks that exact main SHA and all three publication jobs before calling `release.sh`. No GitHub secret or incoming CI connection is required. Configure required reviewers on `production` if available for this repository/account.
7. Create a private OCI Object Storage bucket `qmanga-backups` in Frankfurt. Use an IAM dynamic group matching **only this instance OCID** and a policy limited to that bucket's read/create/overwrite/inspect object permissions; do not grant object deletion. Install the official OCI CLI at `/opt/qmanga/bin/oci` and `install -m 700 deploy/offsite-oci.sh /opt/qmanga/hooks/offsite-backup`. This hook uses instance-principal authentication, uploads both archives and `SHA256SUMS`, downloads each one to a temporary directory for byte and checksum verification, then uploads a `COMPLETE` marker. No long-lived storage key is needed on disk. The production release refuses to run without a successful hook. Arrange regular backups independently of releases too; deployment backups alone do not protect against failures between updates. Monitor the Always Free Object Storage quota (10 GiB Standard in this tenancy) before real media grows.

`deploy/bootstrap.sh staging` starts staging PostgreSQL and MinIO, creates private buckets and a restricted application account. `release.sh` invokes bootstrap itself. The host must be `aarch64`; the scripts refuse another architecture. `config/*.env` files are shell-sourced by the owner-controlled deployment scripts, so only the deploy account may edit them.

## Release flow

Push to `main` runs the existing full acceptance suite. Only a successful run publishes API, web and gateway Linux/arm64 images to GHCR, tagged with the exact commit SHA. The host poller checks the main SHA, successful acceptance and three successful publish jobs every five minutes, then calls `deploy/release.sh staging SHA`. The release keeps the active color serving while it pulls and starts the candidate, checks local API/homepage health, switches Caddy, and checks the real HTTPS hostname through the local Caddy listener. OCI does not route a VM's public IP back to that same VM, so an independent external monitor must verify internet reachability. Failure before switch leaves the old route; failure afterward restores it. The old application stack remains warm. One worker runs per environment. Database migrations occur when the candidate API starts, so **every new migration must remain compatible with the currently active application for the rollback window**.

Observe the GitHub `Verify Qmanga` run and `systemctl status qmanga-staging-poll.timer`; verify `https://qmanga-dev.maqsatto.dev/api/v1/health`, the homepage, login, image reading, and staff publishing on staging. Production remains gated on an off-host backup hook, an isolated restore drill and working SMTP. The existing `Promote Qmanga` workflow uses SSH and cannot reach this host while SSH remains operator-only; use the manual host command with the exact SHA after those gates pass. Promotion creates a fresh backup, invokes the off-host hook, and uses the same health-gated switch at `https://qmanga.maqsatto.dev`.

Manual host commands, when investigating a failed automatic run:

```sh
bash /opt/qmanga/repo/deploy/release.sh staging <tested-40-character-sha>
bash /opt/qmanga/repo/deploy/rollback.sh staging
bash /opt/qmanga/repo/deploy/rollback.sh production
docker compose -f /opt/qmanga/repo/deploy/compose.front.yaml -p qmanga-front logs --tail=100 caddy
```

Rollback switches only application containers and traffic. It **does not undo database migrations or user writes**. If a migration is incompatible, restore requires a separate maintenance decision and may lose writes since the backup. Never run `docker compose down -v` on these projects.

## Recovery and monitoring

Each backup contains `postgres.dump`, `objects.tar`, `SHA256SUMS` and `COMPLETE`. It is made without pausing readers or writers: the DB snapshot is taken first, then objects are copied. This relies on Qmanga's current immutable S3 object keys and lack of physical deletion. **Change the backup procedure before implementing overwrite or physical object deletion.** An incomplete backup has no `COMPLETE` marker; a failed backup blocks promotion. Keep enough free disk for the largest backup and incoming images.

Before production opening, restore one staging backup into **new, isolated test volumes and a new database**, validate `sha256sum -c SHA256SUMS`, run `pg_restore` against the test database, import both object folders from `objects.tar` into test MinIO, compare bucket object counts and fetch sample source/derivative objects. Then start the tested application against that restored environment, verify login, catalogue, reader and publishing, and record the tested backup/SHA/time. Only after this real drill create `/opt/qmanga/state/production.restore-verified`. Repeat the drill regularly and whenever the backup format or storage layer changes. Never restore over live staging or production volumes for a drill.

Check both public `/api/v1/health` URLs, homepage and TLS certificates with external monitoring every few minutes. Alert on failures, disk usage, Docker restarts, backup-hook failures and certificate renewal. SSH access, CI, GHCR, DNS, TLS, SMTP and off-host backup are all operational dependencies. The first real release must be observed on the VM and in a browser; configuration validation alone does not establish uptime.
