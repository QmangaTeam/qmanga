# Qmanga deployment runbook

Only `qmanga.maqsatto.dev` is public. Staging remains on the Oracle Ampere A1 host as an internal release gate, reachable on its loopback gateway ports over SSH. The environments use separate Compose projects, PostgreSQL databases, MinIO volumes and credentials. This is **one-host fault tolerance during application updates**, not high availability if Oracle, the VM, its disk or the network fails.

## Development, integration and acceptance contract

This section is the working contract for Backlog tasks, not evidence that a particular release passed. Use the existing [architecture boundaries](../ARCHITECTURE.md) and [local test environment](../LOCAL-DEVELOPMENT.md).

1. Read the selected Backlog task, dependencies and acceptance criteria; compare them with current code. Assign one owner, set `In Progress`, and record the current plan in that card. Keep each change independently reviewable and commit after appropriate checks. A task on the board is not authorization to expand the current request.
2. Choose checks at the boundary that can fail. For a bug, reproduce it with a failing regression before the fix. Add browser regressions to `apps/web/tests/browser/*.test.mjs`; the existing CI glob includes new files automatically. A static/SSR check does not replace interaction or real persistence checks.

| Change boundary | Contract to preserve | Required evidence for that change |
| --- | --- | --- |
| Presentation → application | Existing ports, truthful loading/error/success state, retained input on errors, kk/ru, both themes, keyboard and reduced motion | Frontend application and SSR tests, app/preview diagnostics, architecture/contrast, production build; browser regression at 320/360/desktop for changed interactions |
| HTTP → use case → PostgreSQL | Auth/role enforcement, validated DTOs, explicit conflict/version semantics, correct transaction boundaries, persisted results | Relevant Go unit/adapter/HTTP tests and real PostgreSQL integration; browser/API acceptance for the affected user journey |
| Publishing → worker → media gateway | Private originals, immutable public revisions, safe codecs, retry behavior and authorized derivative delivery | Real PostgreSQL/codec suite plus synthetic publish/read smoke; test replacements against the existing published revision |
| Browser → offline storage | Account isolation, saved-byte completeness, no false success or position loss, safe cache/schema updates | Browser offline/eviction/retry regression with an isolated context; no production fixtures |
| Schema / HTTP shape / cache format | Previous deployed app keeps working during the rollback window; old clients/data remain readable or have an explicit transition | Backward-compatible migration/adapter tests; document the rollout sequence in the card before changing the contract |
| CI / Backlog / deployment | Locked dependencies, acyclic task identities/dependencies, complete test results, tested SHA only | Locked install and `backlog doctor`, config/shell checks and affected release/backup tests; observed Actions result before claiming remote CI success |

3. Run local checks in a disposable environment where data fixtures are needed. In CI, after the auth/publishing/reading smoke phase and before browsers, recreate only the API from the same built image and wait for health. The browser workflow also separates serial files into groups of eight and recreates that same API between completed groups. This isolates the ephemeral per-IP authentication budget without weakening the production limit; PostgreSQL sessions/fixtures and MinIO media remain intact and the browser phase also exercises restart persistence. Never point seeding or cleanup at production, or reuse the owner's real data as a fixture. Keep credentials in ignored env/fixture files. Use serial full builds to avoid memory pressure. For UI changes rebuild and inspect the integrated Docker web service, not just a preview.
4. Record the code commit SHA, commands/results, failed or unperformed checks, and the concrete next step in the same card. Keep screenshots/logs under ignored `tmp/`; don't create a new report per session. Set `Review` after implementation when remote CI, user acceptance or release gates remain. Docs/tooling tasks may be `Done` after their own verified criteria; product tasks requiring release remain `Review` until that release is observed.
5. On an authorized push/PR, `Verify Qmanga` checks locked Backlog data, setup/deployment definitions, cold Docker start, full Go/PostgreSQL/codec tests without actual skips, auth/publishing/reading smoke, and all browser regressions. Images publish only after successful acceptance on `main`. Inspect the run for the **same SHA**; workflow configuration or a local green build is not a remote result. Push remains subject to the owner's working instructions.
6. On staging, verify that exact SHA, readiness and the changed user journey, including failure/role cases. The host poller and optional GitHub staging job are described below; don't enable a second deployment path or change host access as part of a product task. Record the observed environment/SHA/checks in the card.
7. Promote the same staging images through the existing production gates: verified off-host backup, restore drill, SMTP and health checks. Observe the public changed journey, then mark the product task `Done`. If the candidate fails, use the existing application rollback; database writes and migrations are not reverted. A destructive restore needs its own maintenance decision. No automatic force-push, schema rollback or volume deletion is part of ordinary development.

## Before the first release

1. In the Oracle home region, check actual Always Free capacity and create an **ARM64** Ubuntu VM with at least 2 OCPU, 12 GB RAM and enough persistent disk for two sites, two warm application versions and two backups. Reserve a stable public IP if available. Keep a separate off-host backup destination; a second folder on this VM is insufficient.
2. Set OCI network rules and the Ubuntu host firewall for inbound TCP 80/443 from the internet and TCP 22 only from the operator's allowed source. Oracle's Ubuntu image has a separate iptables `INPUT` rejection rule; add 80/443 before that rule and persist the change in `/etc/iptables/rules.v4`. Do not expose PostgreSQL, MinIO, API or gateway ports. Install Docker Engine with Compose v2, Git, curl, sha256sum and `flock`. Create a dedicated deploy account and install its **public** SSH key. Docker group access effectively grants root-equivalent host control; restrict this account and key.
3. Create a DNS A record for production only. Do not add an AAAA record unless IPv6 is configured and reachable. Confirm production resolves before expecting TLS issuance. The former `qmanga-dev.maqsatto.dev` DNS record should be removed; staging retains that value only as its internal application origin configuration.
4. Under `/opt/qmanga`, create `repo`, `config`, `state/sites`, `backups`, `bin` and `hooks`. Clone the public repository into `repo`, owned by the deploy account. Copy `deploy/host.env.example` to `config/staging.env` and `config/production.env`, adjusting target and origin. Generate distinct high-entropy alphanumeric secrets for each environment. Set owner-only permissions (`chmod 600`) on both files. Configure real STARTTLS SMTP and a working sender address. Keep all secrets outside Git and GitHub logs.
5. The published GHCR images are public, so the deploy account can pull them without a registry token. If package visibility changes, configure a read-only `read:packages` token in the account's protected home.
6. The VM uses an outbound-only systemd poller for staging. Install `jq`, copy `deploy/qmanga-staging-poll.{service,timer}` to `/etc/systemd/system/`, run `systemctl daemon-reload`, then `systemctl enable --now qmanga-staging-poll.timer`. Keep `QMANGA_STAGING_ENABLED` unset: the alternate GitHub-hosted SSH deployment path is intentionally disabled, since TCP 22 is restricted to the operator IP. A successful push or manual `Verify Qmanga` run publishes all three ARM64 images; the poller checks that exact main SHA and all three publication jobs before calling `release.sh`. No GitHub secret or incoming CI connection is required. Configure required reviewers on `production` if available for this repository/account.
7. Create a private OCI Object Storage bucket `qmanga-backups` in Frankfurt. Use an IAM dynamic group matching **only this instance OCID** and a policy limited to that bucket's read/create/overwrite/inspect object permissions; do not grant object deletion. Install the official OCI CLI at `/opt/qmanga/bin/oci` and `install -m 700 deploy/offsite-oci.sh /opt/qmanga/hooks/offsite-backup`. This hook uses instance-principal authentication, uploads both archives and `SHA256SUMS`, downloads each one to a temporary directory for byte and checksum verification, then uploads a `COMPLETE` marker. No long-lived storage key is needed on disk. The production release refuses to run without a successful hook. Arrange regular backups independently of releases too; deployment backups alone do not protect against failures between updates. Monitor the Always Free Object Storage quota (10 GiB Standard in this tenancy) before real media grows.

`deploy/bootstrap.sh staging` starts staging PostgreSQL and MinIO, creates private buckets and a restricted application account. `release.sh` invokes bootstrap itself. The host must be `aarch64`; the scripts refuse another architecture. `config/*.env` files are shell-sourced by the owner-controlled deployment scripts, so only the deploy account may edit them.

## Release flow

Push to `main` runs the full acceptance suite in two isolated CI jobs. Each repeats setup, Go and publishing checks, then runs a disjoint half of the browser files serially. Images publish only after both jobs succeed. API, web and gateway Linux/arm64 images in GHCR are tagged with the exact commit SHA; image jobs use native ARM64 runners. The host poller checks the main SHA, successful acceptance and three successful publish jobs every five minutes, then calls `deploy/release.sh staging SHA`. The release pulls and starts the candidate, checks its API/homepage through the loopback gateway, and leaves the previous stack warm. Staging has no public Caddy route. Production switches Caddy after local health passes and checks HTTPS through the local Caddy listener; an independent external check verifies internet reachability. One worker runs per environment. Database migrations occur when the candidate API starts, so **every new migration must remain compatible with the currently active application for the rollback window**.

Observe the GitHub `Verify Qmanga` run and `systemctl status qmanga-staging-poll.timer`; verify the exact staging SHA and API/homepage through the active loopback gateway with `Host: qmanga-dev.maqsatto.dev`. Exercise changed journeys through an SSH tunnel when needed. Production remains gated on an off-host backup hook, an isolated restore drill and working SMTP. The existing `Promote Qmanga` workflow uses SSH and cannot reach this host while SSH remains operator-only; use the manual host command with the exact SHA after those gates pass. Promotion creates a fresh backup, invokes the off-host hook, and uses the same health-gated switch at `https://qmanga.maqsatto.dev`.

Manual host commands, when investigating a failed automatic run:

```sh
bash /opt/qmanga/repo/deploy/release.sh staging <tested-40-character-sha>
bash /opt/qmanga/repo/deploy/rollback.sh staging
bash /opt/qmanga/repo/deploy/rollback.sh production
docker compose -f /opt/qmanga/repo/deploy/compose.front.yaml -p qmanga-front logs --tail=100 caddy
```

Rollback switches only application containers and traffic. It **does not undo database migrations or user writes**. If a migration is incompatible, restore requires a separate maintenance decision and may lose writes since the backup. Never run `docker compose down -v` on these projects.

## Recovery and monitoring

Each backup contains `postgres.dump`, `objects.tar`, `SHA256SUMS` and `COMPLETE`. It is made without pausing readers or writers: the DB snapshot is taken first, then objects are copied. S3 object keys remain immutable. Physical avatar deletion is serialized against backups by PostgreSQL session advisory lock `(482161, 1)`: the collector takes a nonblocking guard and skips cleanup while backup holds it; a backup refuses to start while another backup or collector owns the guard (retry after that operation finishes); `backup.sh` acknowledges acquisition before `pg_dump`, retains the same live database session through both bucket mirrors, and verifies its backend/lock before marking the backup complete. A lost session/lock fails the backup without `COMPLETE`; shell traps release the guard on failure. Uploads, reading and normal database writes continue. Before relying on this guard, deploy the guarded collector to every API/worker instance in all active stacks and install the matching backup script; an older collector that physically deletes avatars does not observe the lock. Other physical deletion paths or bucket lifecycle rules must use this same protocol or be disabled; do not introduce unguarded overwrite/deletion. An incomplete backup has no `COMPLETE` marker; a failed backup blocks promotion. Keep enough free disk for the largest backup and incoming images.

Before production opening, restore one staging backup into **new, isolated test volumes and a new database**, validate `sha256sum -c SHA256SUMS`, run `pg_restore` against the test database, import both object folders from `objects.tar` into test MinIO, compare bucket object counts and fetch sample source/derivative objects. Then start the tested application against that restored environment, verify login, catalogue, reader and publishing, and record the tested backup/SHA/time. Only after this real drill create `/opt/qmanga/state/production.restore-verified`. Repeat the drill regularly and whenever the backup format or storage layer changes. Never restore over live staging or production volumes for a drill.

Check the production public `/api/v1/health` URL, homepage and TLS certificate with external monitoring every few minutes. Monitor staging locally on the VM. Alert on failures, disk usage, Docker restarts, backup-hook failures and certificate renewal. SSH access, CI, GHCR, DNS, TLS, SMTP and off-host backup are all operational dependencies. The first real release must be observed on the VM and in a browser; configuration validation alone does not establish uptime.

### Google OpenID Connect setup and acceptance

Google sign-in is disabled when both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are absent. Configure both on the API server only, in its private environment file or secret store; never in frontend environment variables, source control, screenshots or Backlog notes. A partial pair is a configuration error. Existing email/password sign-in stays available.

The owner must use their own Google Cloud project and create an OAuth **Web application** client. Configure the consent screen (application name, verified domain, homepage, privacy/contact details) and only `openid email profile` scopes. Add the exact callback for each approved deployment: `https://<deployment-domain>/api/v1/auth/google/callback` (local development may use `http://localhost:<web-port>/api/v1/auth/google/callback`). Register the exact test and production domains/redirects; wildcards and internal container addresses are inappropriate. The owner's personal Google login is a console credential, never a product setting or public support address.

Before enabling in production, verify domain ownership, consent publishing status and test-user restrictions in that owner project. Supply the actual client ID/secret through the server's existing deployment mechanism and restart the API. Check `/api/v1/auth/google/status` reports enabled, then exercise consent, cancellation back to the originating page, registration with the verified Google profile defaults and repeat sign-in. A Google identity whose **verified** email matches a password-registered, non-blocked account links to that account automatically (owner decision 2026-10-19, TASK-62): profile, role and ID stay untouched and the login succeeds; a blocked matched account and a Google already linked to another account are refused with the conflict notice; one user keeps exactly one Google identity (PK `(issuer,subject)`, `UNIQUE(issuer,user_id)`). The settings link flow (verified account, CSRF, expected-account and the exact initiating session, transactional recheck) remains for accounts whose emails differ. Check a blocked account cannot sign in and old callback URLs cannot replay a session. Record the deployed SHA and test-account acceptance without recording authorization codes or tokens.

The server uses authorization-code flow with S256 PKCE, a ten-minute one-use state bound to an HttpOnly SameSite cookie, nonce validation and RS256 ID-token verification (Google issuer, client audience, expiry and authorized party). It requires a verified email and stable Google subject; sessions are ordinary Qmanga sessions. Access/refresh tokens are not persisted. A successful callback issues a 60-second HttpOnly completion proof bound to its consumed state and new session, then passes through the one-use `/auth/complete` server check before the browser clears previous account caches and broadcasts the account transition to other tabs. Unmarked, replayed or wrong-session completion URLs cannot clear caches; cancelled or failed consent does not trigger cleanup. A new Google account receives a display name and verified email from the validated identity and a sanitized avatar from an allowed Google image origin; later sign-ins preserve existing profile edits. Accounts that already have an external identity are selected by issuer/subject; an unlinked password-registered account is auto-linked only by verified email match per the owner decision in the paragraph above.

Local owner acceptance on 2026-10-19 verified the Google Cloud web client, authorized domain and three exact callback URIs (local, staging and production). A new server-only client secret is stored in the ignored local `.env` with mode `0600`; no secret is stored in Git. Real Google consent and ID-token validation succeeded, followed by nickname `maqsatto` and an ordinary verified Qmanga session. This is local acceptance, not an observed remote release.

The project currently requests only `openid email profile`. Google's [basic identity scope exception for Testing](https://support.google.com/cloud/answer/15549945?hl=en) means these requests do not require membership in the test-user allowlist; the local owner login succeeded without adding test users. Reassess that exception if scopes change. Historical local acceptance above does not describe the latest release. Current access instructions and the observed remote release checkpoint are in [OPERATIONS.md](OPERATIONS.md); inspect live state before continuing.
