# Qmanga release design

Historical design from 2026-10-18. For the current internal-only staging deployment and release procedure, use [RUNBOOK.md](RUNBOOK.md) and [OPERATIONS.md](OPERATIONS.md).

Two public origins are planned: `qmanga-dev.maqsatto.dev` (staging) and `qmanga.maqsatto.dev` (production). Both can run on one Oracle Ampere A1 VM, but they must have separate Compose projects, PostgreSQL volumes, MinIO volumes, application secrets and SMTP configuration. Only Caddy publishes ports 80/443. Database, object storage and application gateways remain private or bound to loopback.

GitHub CI already tests the application. A successful push to `main` builds immutable Linux/arm64 API, web and gateway images tagged with the commit SHA in GHCR. The same images are deployed automatically to staging once the owner enables its environment. Production promotes an already tested SHA through a manual GitHub workflow and its protected environment; it never builds different code.

On the VM, the blue and green application stacks share only their environment's database and object storage. A candidate starts while the active stack keeps serving. Caddy switches one origin only after the candidate gateway and public smoke checks pass. One worker per environment is active at a time. Failed candidate preparation leaves the old route untouched; failed post-switch checks restore the old route and worker. The prior color is kept available for explicit rollback. This is a health-gated release, not a claim that a single VM or incompatible database migration can never interrupt service.

Production release must first produce an online database + MinIO backup, record checksums, and store a verified copy away from the VM. Database dump precedes object copy; correctness depends on the current application invariant that S3 object keys are never overwritten or physically deleted. This procedure must change before adding object deletion or key reuse. A migration is backward compatible with the old release until its rollback window ends. Automatic rollback restores application images/routing, never reverses database migrations or user writes. Backup restoration is tested on staging before opening production to readers.

The host configuration and secrets live outside the Git checkout under `/opt/qmanga/config`; GitHub holds a restricted SSH deployment key and pinned SSH host key. OCI, DNS and GitHub environment settings are created only after account access is available. The VM's actual Always Free allowance, capacity, disk and egress are confirmed in its home region before provisioning.

Acceptance: independent staging/production data; no accidental port exposure; untrusted X-Forwarded-For cannot bypass identity throttling; tested SHA only; candidate health gate; simulated pre- and post-switch failure preserves or restores old traffic; production backup + restore; HTTPS on both requested names; end-to-end smoke after deployment; explicit rollback from the same release image.
