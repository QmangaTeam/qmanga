# Редизайн Qmanga через компоненты

Дата: 17 октября 2026 года. Направление и порядок работы подтверждены владельцем: сначала компоненты, затем сборка экранов; новую продуктовую функциональность разрабатывать после редизайна. Эта спецификация описывает конкретный состав работ и ожидает проверки владельцем перед подготовкой плана реализации.

## Цель и границы

Qmanga должна выглядеть как удобная библиотека для чтения, а не рекламный лендинг. Основная аудитория читает казахские переводы с телефона, в том числе при плохой связи. Сохраняем существующие цвета и работающие сценарии; меняем композицию, плотность, повторяемость элементов и язык интерфейса.

В редизайн входят общие компоненты, все существующие экраны и ранее запрошенный Kazakh-first / Russian UI. Переключатель языка — часть этого UI-прохода, а не перевод контента. Расширение каталога, новые поисковые возможности, профили, новые ленты, подписки и другие продуктовые дополнения из сравнительного аудита отложены.

Работа ведётся непосредственно в `outputs/qmanga`, самостоятельно, без AGY. После проверенных этапов — отдельные коммиты и отправка в существующий приватный репозиторий. Новый проект, ветка, библиотека UI или внешний сервис не нужны.

## Визуальный контракт

### Цвета и типографика

Существующие роли и значения цветов сохраняются:

| Роль | Тёмная тема | Светлая тема |
| --- | --- | --- |
| Фон | `#0d1117` | `#f6f8f3` |
| Поверхность | `#161c25` | `#ffffff` |
| Приподнятая поверхность | `#202835` | `#edf1e8` |
| Разделитель | `#29323e` | `#d9dfd3` |
| Основной текст | `#edf2f5` | `#172217` |
| Вторичный текст | `#96a2b2` | `#65715f` |
| Акцент | `#b4ee69` | `#486c1d` |
| Текст на акценте | `#17220d` | `#ffffff` |

Зелёный обозначает основное действие, выбор или текущую позицию, а не украшает каждый заголовок. Статус нельзя передавать только цветом. Слабый цвет разделителя не используется как единственный признак доступности поля или его состояния.

Системный шрифт с казахской кириллицей, без загрузки новых шрифтов. Основной текст и ввод — 16px, метаданные — 13–14px, подписи мобильной навигации — 12px, заголовок страницы — 24px на телефоне и 28px на широком экране. Никаких рекламных заголовков на 50–60px. Рабочая шкала отступов: 4, 8, 12, 16, 24, 32px; скругления: 6px для обложек, 8px для контролов, 12px для отдельных панелей.

### Композиция

- Шапка высотой 56px, компактный существующий бренд, без декоративных стрелок возле каждой ссылки. В читалке остаётся собственная оболочка.
- Поля страницы: 16px на телефоне, 24px на десктопе; максимальная ширина основного контейнера 1200px. На 320px содержимое сжимается или переносится, а не вызывает горизонтальный скролл всей страницы.
- Пять существующих мобильных направлений сохраняются. Нижняя панель учитывает safe area; последний элемент страницы и фокус не перекрываются ею. Десктопная навигация оставляет доступ ко всем направлениям, не скрывая их только за мобильной панелью.
- Обложки — сетка, главы и обновления — строки с разделителями, настройки — смысловые группы, формы — поля с подписями. Не превращаем всё в одинаковые большие карточки.
- Сетка каталога: 2 колонки на 320–639px, 3 на 640–767px, 4 на 768–1023px, 5 от 1024px. Обложки с одинаковым отношением сторон 7:10; названия до двух строк и полное доступное имя ссылки. Отсутствующая обложка — нейтральный placeholder, не сгенерированный арт.
- Из первого экрана убираются hero, Q с орбитой, слоганы, буквенные декоративные блоки и повторяющиеся uppercase-подписи. Внешний вид формируется реальными обложками, именами и читаемыми строками, а не новыми декоративными эффектами.

## Этап 1 — компоненты до экранов

Компоненты создаются и проверяются отдельно до переноса рабочих страниц. Не строим универсальную библиотеку на все случаи: только элементы, нужные существующим сценариям.

### Общие примитивы

Размещение: `apps/web/src/lib/shared/presentation/ui/`. Общие стилевые токены остаются в presentation и подключаются через `app.css`; старые селекторы удаляются только после переноса их потребителей.

| Компонент | Ответственность и состояния |
| --- | --- |
| `Button` | Настоящий button; primary / secondary / ghost / danger, обычный / disabled / busy. По умолчанию `type="button"`; submit задаётся явно. Busy предотвращает повторное действие и объявляется через `aria-busy`, disabled не изображает загрузку курсором |
| `ActionLink` | Навигационная ссылка, визуально согласованная с кнопкой, но без имитации disabled и без вложенного button |
| `Icon` и `IconButton` | Небольшой набор собственных SVG-иконок; декоративная иконка скрыта от accessibility tree, кнопке обязательно доступное имя и цель не меньше 44×44px |
| `Field` | Подпись, слот существующего input/select/textarea, описание и ошибка через связанные ID; обязательность, disabled и ошибка различимы не только цветом |
| `Badge` | Некликабельная метка типа, статуса или явно тестового материала; не маскируется под кнопку |
| `SectionHeading` | Один смысловой заголовок, необязательные описание и существующее действие; без рекламного eyebrow |
| `StateMessage` | Раздельные empty / loading / error / offline / success. Предлагает только реально подключённое действие; ошибки не подменяются пустым результатом |
| `SettingsRow` | Подпись и пояснение рядом с контролом, на узком экране контроль переносится ниже. Не связывает UI с хранилищем настроек |
| `Pager` | Только существующие переходы по страницам/курсору; различает недоступный переход и выполняющуюся загрузку |

Примитивы принимают типизированные props, callbacks и Svelte snippets. Они не знают об аккаунтах, публикациях, HTTP, cookies, IndexedDB или MinIO. Не нужен общий «базовый компонент» с десятками несвязанных флагов. Поиск использует обычный GET-form и общий `Field`; отдельный сложный поиск-компонент пока не нужен.

### Продуктовые компоненты

Они остаются в presentation своего контекста, а не переносят бизнес-модели в shared:

- Catalog: `CoverCard` и `ChapterRow`, использующие существующие read models. Отдельные ссылки команды и чтения не вкладываются в одну большую ссылку.
- Reading: `LibraryRow` для существующего прогресса, статуса и действий. Нет новых вычислений непрочитанных или правил разрешения конфликтов внутри Svelte.
- Общая оболочка: `AppHeader` и `MobileNavigation`, активный маршрут и локализованные подписи получают снаружи. Читалка не получает вторую общесайтовую панель.
- Identity: общий каркас формы, использующий примитивы, но существующие submit-сценарии остаются у `AuthForm`.

Для ревью компонентов нужен изолированный демонстрационный экран в development/test-среде с явной надписью «UI preview»: длинные казахские и русские строки, обе темы, все состояния, клавиатурная навигация. Он не попадает в публичные production-маршруты и не использует аккаунты или чужую мангу. Отдельный Storybook и тяжёлый runtime не устанавливаются. Проверки семантики компонентов должны быть повторяемыми, не только скриншотами.

## Этап 2 — сборка существующих экранов

После проверки компонентов страницы собираются из них в следующем порядке:

1. **Оболочка, настройки, вход и регистрация.** Компактная навигация, прямые заголовки «Кіру» / «Тіркелу», понятные подписи полей, без повторного брендинга и рекламных вступлений. Сохранить восстановление пароля, подтверждение почты, logout и проверки ролей.
2. **Каталог и главная.** Каталог сохраняет текущие фильтры, URL и пагинацию. Главная получает компактный поиск в существующий каталог и обложки из его существующего публичного read model с сортировкой по обновлению. Не выдавать обновление тайтла за новую главу. Нет нового endpoint, вымышленного топа, личного продолжения или ленты глав; их разработка — следующий функциональный этап. При ошибке каталога показать ошибку и существующую ссылку, при действительно пустом каталоге — пустое состояние.
3. **Тайтл, библиотека, команда и уведомления.** В route тайтла уже подключены `LibrarySelection` и `Discussion`: переиспользовать и лучше разместить их, а не считать отсутствующими. LibrarySelection расположить после шапки и до длинного списка глав; существующее продолжение показывать только при наличии прогресса. Обложка/метаданные, описание, команды, главы и обсуждение получают разную иерархию. Не добавлять новый глобальный алгоритм «начать чтение», поиск глав, вкладки с новым поведением или функциональность профиля.
4. **Сохранённые главы и читалки.** Привести тексты, кнопки, поля и панели к системе; сохранить текущую image-first композицию. Не менять scheduler, quality policy, контроллер, направления управления, номера страниц, прогресс, загрузки или обработку ошибок ради внешнего сходства. Справа остаётся «вперёд» по умолчанию, включая RTL-источники. Полноэкранная мобильная и боковая десктопная панели остаются доступны.
5. **Студия, публикация, каталог администратора и модерация.** Рабочие списки, формы и статусы на тех же компонентах. На телефоне действия и состояние доступны без hover и горизонтального поиска. Не расширять права, форматы загрузки, ревью или модель публикации.

Во время переноса каждого экрана проверить его реальные действия. Редизайн не должен удалить редко используемые существующие элементы под предлогом минимализма. Неподключённые действия и фиктивные данные не используются как декоративные заглушки.

## Kazakh-first и Russian UI

Первый визит — `kk`, независимо от языка устройства. Явный переключатель «Қазақша / Русский» находится в настройках; выбранный язык можно сменить также из настроек читалки, не покидая чтение. Значение сохраняется на устройстве, но не требует нового поля аккаунта или API.

SSR получает `kk` или `ru` из проверенной cookie `qmanga_locale`; неизвестное значение означает `kk`. Browser adapter сохраняет тот же выбор в локальном хранилище для офлайна. Без доступа к хранилищу переключение продолжает работать в текущей вкладке. Для обычной сетевой страницы cookie — источник SSR-выбора; для офлайн-оболочки — локально сохранённый выбор, по умолчанию `kk`.

Локализация — presentation concern. Чистые типы локали и коды результата допустимы в shared/domain; словари, форматирование и Svelte context — в shared/presentation. Адаптеры cookies/storage подключаются только в entry points/composition; компоненты не читают хранилище напрямую. Контекст создаётся на экземпляр layout/запрос, не как изменяемая переменная всего сервера. Строки общих компонентов передаются явно, словари предметных экранов остаются рядом с presentation контекста.

UI выводит сообщения по стабильным кодам/типизированным результатам, а не переводит готовый казахский текст строковыми заменами. Уже существующий Go error code маппится адаптером; неизвестная ошибка получает понятное локализованное сообщение, а не сырой текст сервера. Фронтенд-результаты с захардкоженными сообщениями переводятся на коды без изменения правил валидации. Go API, БД и доменные инварианты не меняются ради UI.

Перевод охватывает навигацию, заголовки, формы, существующие статусы, validation/error/loading/offline-состояния, reader, библиотеку, студию, админку, доступные имена, заголовки документов и сообщения SvelteKit 404/503. Числа и даты форматируются через `Intl` с `kk-KZ` / `ru-RU`. Пользовательские названия, описания, комментарии, имена команд, страницы манги и содержимое писем не переводятся UI-переключателем.

Использовать «Аккаунт», «Команда», «Каталог» и обычные казахские действия; «Профиль» — только там, где действительно есть профиль. Удалить «Есептікжазба», не заменяя понятные казахские слова русскими предложениями. Локаль не меняет reading URL, release/team ID, progress key, качество или выбор перевода.

Офлайн-оболочка остаётся общей и не содержит аккаунтных данных. Сетевой HTML с локалью из cookie получает `Cache-Control: private, no-store`, включая обычную читалку; существующие правила кэширования медиа и статических файлов не меняются. Не кэшировать cookie-варианты `/offline-reader` под одним публичным ключом: общая оболочка всегда стартует с `kk`, а локальный adapter применяет сохранённый язык. Статические словари доступны офлайн без отдельного запроса.

## Архитектура и производительность

Сохраняются [Clean Architecture / DDD](../../ARCHITECTURE.md) и существующие context boundaries. Маршруты связывают зависимости; presentation отображает state и вызывает текущие use cases. Ни fetch, ни cookies, ни storage не переносить в примитивы или feature-компоненты. Внешние ошибки маппятся в infrastructure; бизнес-правила не зависят от Svelte или локали.

Все обложки и страницы остаются за Go media gateway. Сохраняются SSR каталога, lazy loading вне первого экрана, размеры изображений против скачков layout и ограниченная очередь reader. Никаких новых шрифтов, animation-фреймворков, icon-fonts и обязательной загрузки всех обложек/глав ради редизайна. Потребность в дополнительных application/view-model модулях определяется повторяемой логикой, а не желанием создать слой на каждый элемент.

## Приёмка

- Сначала доступны проверенные примитивы и продуктовые компоненты; рабочие экраны переносятся только после этого этапа. Все текущие роли и маршруты сохраняют реальные действия.
- Проверки ширины 320, 360, 768 и 1280px; обе темы и оба языка, длинные заголовки/метки, 200% zoom, клавиатура, видимый фокус и reduced motion. Цели интерактивных элементов минимум 44×44px, включая иконки. Читалка проверяется также при малой высоте и в landscape.
- Обычный текст: контраст минимум 4.5:1, крупный текст и необходимые границы контролов/индикаторы — 3:1. Проверяются реальные сочетания цветов, не только наличие CSS-токенов. Существующие цвета можно использовать в другой роли, не заменяя палитру.
- Empty, loading, failure, offline и populated — разные состояния. Тестовые материалы явно помечены; нет «главы скоро» при непустом каталоге или обещания отсутствующей кнопки.
- Локали: отсутствие выбора, сохранённые `kk` / `ru`, неправильная cookie, запрет storage, параллельные SSR-запросы на разных языках и офлайн-возврат. Нет смешивания пользовательских данных/языка между запросами и сброса прогресса при переключении.
- Регрессии: чтение мышью/тапами/клавиатурой, границы страниц и глав, сохранённые главы, login/logout, библиотека, сообщения/жалобы и существующий upload/review. Используются локальные тестовые аккаунты, без паролей и приватных данных в Git или screenshots.
- Для каждого переноса: целевые тесты, architecture check, Svelte check и production build; финальный проход в работающем Alpine Docker-окружении и screenshots. Эмуляция не считается тестом на физическом слабом Android; такая проверка остаётся отдельным требованием перед публичной бетой.
