# Qmanga и чтение на слабом телефоне

Проект требований к читалке. Дата: 17 октября 2026 года. Числа ниже — исходные бюджеты и условия приёмки Qmanga, а не результаты измерения Senkuro или уже работающего приложения.

## Основной сценарий

Читатель открывает главу по ссылке, получает название и первую страницу, читает и закрывает вкладку. При возвращении попадает на прежнее место. Обрыв связи не сбрасывает главу, а слабое устройство не обязано держать в памяти все изображения. Хорошее соединение позволяет выбрать высокое качество без повторного открытия главы.

В MVP два режима: вертикальная лента и отдельные страницы. Для вебтунов по умолчанию лента, для обычной манги — страницы; предпочтение пользователя важнее значения по умолчанию. Направление оригинала LTR/RTL не задаёт направление управления: для нашей аудитории справа всегда следующий номер по умолчанию. Обратное управление в режиме страниц включается только вручную. Вертикальная лента всегда идёт сверху вниз.

Касание крайних30% изображения, боковые кнопки и стрелки клавиатуры используют одно направление. В обоих режимах по умолчанию справа/ArrowRight — следующая исходная страница, слева/ArrowLeft — предыдущая. Только явный выбор обратного управления в режиме страниц меняет стороны согласованно во всех трёх способах. Сохранённое старое значение auto теперь означает обычное управление, а не наследование RTL тайтла. Центральные40% не перелистывают, вертикальная прокрутка и нативный pinch zoom сохранены. На границах главы кнопки отключены; следующая глава выбирается отдельно, без смены команды. Счётчик допускает округление границы до1px, чтобы браузер не возвращал номер предыдущей страницы после перехода.

На экране остаются изображение, компактный индикатор позиции и доступ к управлению касанием. Верхняя панель содержит возврат и главу, нижняя — страницы, главы и настройки. При открытой панели нажатие Android «Назад» закрывает её. Свайп может быть удобным дополнением, но каждое действие доступно обычной кнопкой. В MVP нет сложного собственного движка масштабирования: сохраняем нативный pinch zoom и кнопку более качественного изображения.

## Режимы качества

Качество и экономия памяти — разные настройки. На слабом телефоне разрешено высокое качество с маленьким окном загрузки. На быстром телефоне можно экономить мобильный трафик.

| Выбор читателя | Файлы и поведение | Предзагрузка |
| --- | --- | --- |
| Авто | Начинает со стандартного варианта; Save-Data предлагает экономию, наблюдаемые задержки могут понизить последующие загрузки | 1 следующий фрагмент, до 2 при устойчиво быстрой загрузке |
| Үнемдеу | Вариант eco, меньшие файлы; счётчик примерного объёма главы | 1 следующий, без автоматической следующей главы |
| Қалыпты | Вариант standard, баланс текста и размера | 1–2 следующих в пределах бюджета памяти |
| Жоғары | Вариант high, максимальная чёткость подготовленного изображения | То же ограниченное окно; высокое качество не означает загрузку всей главы |
| Оригинал | Явно открыть исходную страницу с предупреждением о её размере | Не загружается автоматически |

Исходные профили для проверки на реальном контенте: eco до 720 px по ширине, standard до 1080 px, high до 1600 px; никогда не увеличивать маленький оригинал. Если в eco теряются казахские буквы или мелкие реплики, повысить разрешение/качество именно для этого изображения. Не задавать один JPEG quality для всех рисунков и считать задачу решённой.

Основной оптимизированный формат — WebP, резервный — JPEG для непрозрачных страниц и PNG там, где нужна прозрачность или сохранение линий. AVIF можно оценить позднее на конкретных слабых устройствах: меньший файл сам по себе не доказывает меньшую задержку декодирования. Выбор формата не должен ломать заявленный браузерный минимум.

Реализованный pipeline: JPEG/PNG/WebP → worker → WebP eco720/q70, standard1080/q82, high1600/q92, фрагменты не выше2048px и без увеличения маленьких источников. Это сжатие с потерями, не обещание полного отсутствия потерь или уменьшения абсолютно любого файла. Полноразмерная очищенная PNG-копия доступна отдельным явным действием. JPEG-fallback для старых браузеров пока не реализован; базовый целевой Chrome109 уже поддерживает WebP. AVIF не требуется для чтения. Фактический формат, размеры, байты и SHA-256 проверяются тестами и локальным smoke через Go, не только расширением файла. Совместимость формата описана в [официальном WebP FAQ](https://developers.google.com/speed/webp/faq); поддержка формата не равна проверке всего приложения на физическом устройстве.

У каждой страницы в manifest есть исходные размеры, связь с фрагментами, доступные профили, mime и размер в байтах. Интерфейс оценивает размер главы суммой файлов выбранного профиля; это размер медиа, без обещания точного сетевого расхода с накладными расходами и повторами.

При ручном выборе режим не меняется самостоятельно. В авто понижение применяется к ещё не загруженным изображениям и показывает причину. Повышение предлагается читателю после устойчивого улучшения, чтобы не тратить мобильный трафик неожиданно. Network Information API используется только как подсказка: он имеет [ограниченную поддержку браузерами](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation).

## Как переключается качество

1. Текущее положение описывается исходной страницей и вертикальной долей, а не только номером нарезанного фрагмента.
2. Новое качество сначала загружается для видимой области. Старое изображение остаётся до успешного декодирования замены.
3. После переключения сохраняется положение относительно содержимого; страница не прыгает в начало.
4. Загруженное eco не заменяется на high во всей главе автоматически. Меняется текущая область и будущие запросы.
5. Кнопка «Оригинал» работает отдельно для конкретной страницы и показывает её реальный размер.

Профили и границы фрагментов строятся по общей системе координат оригинала. На разных ширинах нельзя молча терять или дублировать строку рисунка на стыке.

## Загрузка при нестабильной сети

Первым запрашивается manifest и видимый фрагмент. Не начинать загрузку обложек, комментариев, аватаров или следующей главы до первого изображения. Комментарии открываются по действию читателя, кредиты команды доступны текстом без обязательной загрузки её баннера.

В режиме экономии одновременно выполняются максимум два запроса изображений: видимое и одно следующее. После ухода из главы ненужные запросы отменяются. Подсказки браузеру о [ленивой загрузке](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Lazy_loading) дополняют управляемую очередь, а не заменяют её.

После сетевой ошибки — не более трёх автоматических повторов с паузами примерно 1, 3 и 8 секунд и небольшим случайным смещением. Затем только явный «Қайталау». Для 429 использовать Retry-After; для 404 или withdrawn повтор не запускать. Пока страница скрыта, новые фоновые попытки приостанавливаются. Возврат соединения предлагает повторить видимую ошибочную страницу.

Скачанный полностью объект сохраняется; при следующем запросе используем кеш. Неполный небольшой фрагмент обычно запрашивается заново. Поддержку Range для частичного возобновления не обещаем до отдельной проверки, потому что она зависит от всей цепочки выдачи. У загрузки команды на сервер multipart предусмотрен отдельно.

Не использовать navigator.onLine как доказательство доступности сервера: статус показывает только подсказку, успешность решает реальный запрос. Не загружать отдельный большой тестовый файл для измерения скорости.

## Память и длинные вебтуны

Большая картинка в сжатом виде может занимать мало места, но после декодирования приблизительная память RGBA равна width × height × 4 байта. Например, 1080 × 20 000 — около 82,4 MiB только под пиксели. Поэтому одна огромная вертикальная картинка — плохая единица загрузки для слабого телефона.

Обработчик делит длинные исходники на фрагменты высотой до 2048 px в каждом профиле. Это технические части исходной страницы, а не новые страницы главы. У каждого фрагмента заранее известны размеры и положение в оригинале.

В ленте поддерживаем окно около видимой области. Бюджет одновременно декодированных изображений — ориентир до 40 MiB, а не жёсткое число любых страниц. Обычно это текущий фрагмент, предыдущий и 1–2 следующих; для high окно может стать меньше. Ушедшие изображения заменяются заполнителями с теми же размерами, освобождаются ссылки и object URL. Сетевой/дисковый кеш не равен декодированной памяти.

В режиме страниц держать текущую и соседнюю, а следующую по направлению чтения готовить с приоритетом. После нескольких глав старые массивы DOM и обработчики не должны оставаться в памяти. Полный набор страниц хранится в manifest, но не в виде сотен одновременно декодированных img.

## Сохранение позиции

Локальная позиция записывается с ограниченной частотой, например не чаще раза в 2 секунды, при смене страницы и переходе приложения в фон. Формат: title, project, release, revision, source_page_id, relative_offset, локальная последовательность события. Постоянный скролл не отправляет сетевой запрос на каждый пиксель.

Облачная синхронизация — примерно раз в 15 секунд активного чтения, на завершении главы и при возможности перед уходом. Последняя запись перед закрытием не гарантирована браузером, поэтому основная защита — регулярное локальное сохранение, а не один unload-запрос.

События имеют event_id, device_id, seq и base_server_version. Повторный пакет безопасен. Порядок seq внутри устройства важнее его часов. Если другая сессия уже изменила позицию после base_server_version, старый офлайн-пакет не перезаписывает её молча: сохраняем оба варианта и предлагаем «жалғастыру осы жерден» либо облачную позицию. После решения создаётся новая серверная версия.

Последняя позиция и наиболее дальняя прочитанная глава — отдельные данные. Перечитывание первой главы меняет место продолжения, но не стирает факт прочтения поздних глав. При смене команды прогресс остаётся связан с исходным релизом; перенос на другой перевод предлагает начало той же логической главы.

Гостю сохраняем позицию локально. После входа предлагаем перенести локальный прогресс и явно разрешаем конфликт с облачным. Локальные записи авторизованного пользователя разделены по аккаунтам и очищаются при выходе; сохранённые публичные главы могут остаться по отдельному выбору пользователя.

## Сохранить главу для чтения без сети

В MVP — явное сохранение одной выбранной главы за операцию, без массовой загрузки серии. Несколько глав можно сохранить последовательно в пределах доступного места. Кнопка показывает качество и ожидаемый объём до старта.

Состояния: не сохранена → сохранение N/M → готова; либо ошибка/приостановлена/не хватает места. Глава считается готовой только после проверки наличия manifest и всех файлов выбранного профиля. Частичная загрузка не получает зелёный статус полной готовности.

Service worker кеширует публичную оболочку читалки и опубликованные медиа, а метаданные загрузок и позиции хранятся в IndexedDB. Приватные страницы профиля, сессии, ответы модерации и studio не попадают в общий offline cache. Токен авторизации не нужен для уже сохранённой публичной главы.

После закрытия браузера офлайн-ссылка открывает сохранённую главу через оболочку. Если движок не поддерживает нужные API или хранение отклонено, показываем эту возможность недоступной, но обычное онлайн-чтение продолжает работать. Не требуем установки PWA ради чтения.

Автоматический кеш просмотренных изображений ограничен ориентиром 50 MiB и удаляет старые записи по LRU. Явно сохранённые главы защищены от собственной LRU-очистки приложения, но не от решений браузера. До новой загрузки проверяем StorageManager.estimate; исходный мягкий лимит явных сохранений — минимум из 200 MiB и 20% доступного по оценке остатка квоты. Оценка приблизительна: ошибки QuotaExceeded всё равно обрабатываются.

При недостатке места не удаляем явно сохранённые главы молча: предлагаем удалить выбранные или сохранить в eco. Можно запросить persistent storage, но нельзя обещать положительный ответ. Важно прямо объяснить, что [браузерные квоты и очистка данных](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) могут удалить копии. После запуска сверяем индекс с фактически оставшимися файлами.

Офлайн-режим не отправляет комментарии и оценки скрытно. Для этих действий нужно подключение. Прогресс и изменения личной библиотеки могут стоять в локальной очереди с видимым состоянием ожидания. При сетевой проверке новая ревизия предлагает обновить сохранённую главу; старая копия заменяется после полной загрузки новой.

## Выдача и кеширование

Manifest содержит номер ревизии и ссылки на подготовленные варианты. Он коротко кешируется с проверкой ETag; после снятия релиза новая выдача возвращает withdrawn. Приватные preview manifest доступны только по сессии команды и не кешируются общим кешем.

У производных файлов версионные ключи с checksum/профилем/версией обработчика, поэтому смена ревизии не смешивает старые и новые страницы. Оригиналы и черновики не имеют анонимного пути выдачи. Публичные производные проходят через контролируемую выдачу, которая проверяет статус релиза, а не открытый листинг всего bucket.

Снятие публикации запрещает новые выдачи и запускает удаление управляемых кешей. Уже полученный файл в кеше браузера или офлайн-копия на отключённом телефоне не могут быть надёжно отозваны. Интерфейс не обещает обратного. Добавление CDN возможно без изменения формата manifest, но выбор инфраструктуры вынесен за рамки текущего планирования.

## Бюджеты производительности

| Метрика | Исходная цель |
| --- | --- |
| JS первого открытия читалки | До 100 KiB gzip, без кода studio и модерации |
| HTML + CSS + manifest до первой картинки | До 80 KiB gzip суммарно |
| Первая eco-картинка | Стремиться к 60–150 KiB; разборчивость текста обязательна, исключения измерять |
| Весь старт до первой картинки | Стремиться до 330 KiB с учётом JS и стартовых данных |
| Декодированные изображения около viewport | Ориентир до 40 MiB; профилировать отдельно от общей памяти вкладки |
| Eco относительно high | Медианное уменьшение объёма минимум на 50% на контрольном наборе без потери читаемости |
| Первый eco-фрагмент на 256 kbps и RTT 400 ms | Ориентир до 15 секунд с холодным кешем на контрольных страницах; результаты фиксировать отдельно |
| Возврат в сохранённую главу без сети | Открытие оболочки и позиции без зависания на сетевом ожидании |
| Стабильность ленты | Размер заполнителей удерживает позицию, CLS стремится к ≤ 0,1 |

При 256 kbps передача 330 KiB сама занимает примерно 10,6 секунды без RTT и других накладных расходов. Поэтому красивые цели в 1–2 секунды в таком сценарии не обещаются. После первого замера бюджет корректируется с объяснением, если содержание страницы требует большего файла.

Для нормальной мобильной сети дополнительно ориентируемся на [Core Web Vitals](https://web.dev/articles/vitals): LCP ≤ 2,5 s, INP ≤ 200 ms, CLS ≤ 0,1 на 75-м перцентиле при достаточной полевой выборке. Это отдельный сценарий, он не подменяет тест 256 kbps. На старте без полевых данных сохраняем лабораторные результаты и характеристики устройства.

Конкретный телефон пользователя для приёмки ещё не выбран.

Для контента нужен контрольный набор: чёрно-белые мелкие реплики, цветная манхва, тонкие линии, длинный вебтун, казахские диакритические буквы, слабый исходник и глава с сотнями фрагментов. Не использовать только одну красивую страницу как доказательство качества всей системы.
